**F01：检查器没有证明“实物引脚接对了”。**

对已正确映射的 `D1 vin out 1N4148`，交换 D1 的两个焊盘网络，`check_partition()` 仍返回 `ok=true`。原因是它最终只比较“每个元件在每个网络上有几个脚”，丢弃了具体引脚身份；交换二极管两脚后，这个计数不会变。应按稳定的逻辑引脚、器件引脚功能和实际焊盘编号进行比较，允许的接口转换需独立声明。

此外，正常任务检查使用映射阶段的 `mapped["spec"]`；回导复核通过 [api.py:366](D:/Users/Lenovo/something/开源创新大赛/voltproof/app/pcb/api.py:366) 读取旧 `mapping_report.json` 重建比较对象。两者都未提取最终板文件的真实焊盘网络。即使 DRC 对板内网络给出零违规，也不能据此证明板与源电路一致。本轮用模拟的干净 DRC 响应验证了这条调用路径，未声称真实 KiCad 接受了测试占位文件。

复验要求：交换二极管 A/K、晶体管 C/E、连接器脚号必须失败；在 KiCad 中同步修改焊盘网络和铜线、使板内 DRC 通过时，源电路一致性检查仍应发现未经声明的连接变化。造板适配器还应按焊盘编号赋网，不能依赖 `zip(fp.Pads(), pads)` 的遍历顺序。

**F02：普通网络名称能改变电路拓扑。**

最小输入如下：

```spice
* distinct numeric and named nets
R1 1 N2 1k
R2 N2 0 2k
.end
```

地节点 `0` 首先被重命名；随后数字节点 `1` 被分配名字 `N2`，与已有 `N2` 冲突。R1 的网络从 `[1, N2]` 变成 `[N2, N2]`，映射仍成功。应使用无碰撞的稳定网络 ID，保留原名作为显示名称，并检查规范化前后的连接分区等价。

**F03：仿真元件处理会丢失必要的电气语义。**

`I1 out 0 DC 1m` 被标为 `probe`，映射层只处理 `device` 和 `blocked`，因此它没有阻断、没有外部端口要求、没有明确转换记录，只留下电阻上板。`Vprobe a b DC 0` 的值被解析为字符串 `DC`，绕过零伏检测；声明 a、b 端口后也可通过映射。这两条都违反计划“不静默删除仅仿真元件”的要求。

复验要求：覆盖 `0`、`DC 0`、大小写、带单位数值等合法写法；所有非板上器件都必须有经确认的转换或明确阻断，不能仅靠角色名称跳过。

**F04：检查与导出没有绑定同一份冻结内容。**

导出接口只检查版本状态为 `checked`、它是当前采用版本、产物目录存在，然后返回目录中的文件名与历史板哈希。本轮在临时工作区直接调用接口处理函数，复现了三个情况：空产物目录返回 `ok=true, files=[]`；修改板文件后继续返回旧哈希和导出成功；模拟 DRC 返回两条违规后，`recheck` 报失败，但版本仍为 `checked`，下一次导出照常成功。

源电路改变时，已有 `is_stale()` 能识别部分变化，但导出和采用并未将该结果纳入判定，也没有把导出结果明确标为历史电路产物。计划允许导出明确标记的历史版本，不能把它继续表示为当前电路的有效结果。

应建立检查快照，绑定源电路、实际板、规则、映射库和全部制板文件。内容变化应使旧结论失效；回导修改形成新修订，经检查后重新生成产物。导出必须验证必需文件与哈希，历史导出和当前有效制板包的状态要明确。

**F05：规则记录与实际工具输入脱节。**

通过模拟外部工具并记录调用参数，把线宽由 0.25 mm 改为 2 mm、净距由 0.2 mm 改为 1 mm、过孔钻孔由 0.6 mm 改为 1.5 mm，任务保存了不同规则哈希，但传给造板的规格和传给布线器的选项完全相同。`build_board` 未建立相应项目规则或网络类别，API 提交任务也没有接入制造规则字段。

DRC 命令使用 `--severity-error`，无法满足计划要求的完整警告保留；当前结果也没有展示逐项警告/排除项及处理状态。应将规则落实到板工程、DSN 与检查中，并用真实不满足指定线宽/净距的板证明检查会失败，而不是只验证规则 JSON 成功保存。

**F06：版本记录不足以判定结果是否过期。**

实测 `V1 vin 0 DC 5` 改为 `DC 50`，电气哈希相同；修改 `.model` 参数，哈希也相同。只读取单个值 token、忽略模型定义会漏掉电气变化。映射哈希也只包含库结构版本和条目 ID，没有覆盖具体引脚表与封装内容。

版本记录没有计划中的 `source_version_id`。采用接口的 `expected_revision` 是可选的，前端采用操作未发送它；后端也没有检查源电路修订号。因此目前只有“新任务留下候选”的保护，尚未实现计划要求的完整源电路/PCB 双重修订冲突保护。

复验要求：保留电气语义完整的源快照；参数、模型、实际引脚表或封装改变均应使相关结论失效。两个页面同时采用、源电路在任务途中改变、恢复旧候选等场景，应返回冲突或明确的历史版本状态。

**F07：拖动坐标的含义不一致。**

执行实际 `pcb.js`，使用最小 DOM 适配器模拟拖动：R1 原点 `(10,20)`，两焊盘位于 x=10 和 x=20.16，向右拖动 2 mm。应提交原点 x=12，实际提交 x=17.08，误差 5.08 mm；两个焊盘的显示中心也变得相同。前端用焊盘均值作为移动中心，后端却把该坐标传给封装 `SetPosition`；显示更新还对所有焊盘直接设置同一中心。

应从实际板导出封装原点、方向和局部焊盘坐标，拖动使用统一位移变换，并处理连续拖动和旋转。本反例验证了生产 JS 的计算逻辑，没有代替完整浏览器或真实 KiCad 操作验收。

**建议交还 GLM 的修复顺序与再验收条件**

1. 先修 F01–F03：建立不会丢失元件、节点或引脚身份的映射与实际板一致性检查。增加上述反例及独立人工定义的期望连接，不让预期与实际共用同一错误映射算法。
2. 修 F04、F06：检查结果绑定冻结版本；采用强制校验源电路和 PCB 修订号；回导改变内容后旧结果失效；导出拒绝缺文件、哈希不符和失败复核结果。历史导出须有明确状态。
3. 修 F05：规则写入实际工程、布线输入和检查；保留警告与排除项；用真实违反规则的测试板证明不会误报通过。
4. 修 F07，补齐输出端口、封装确认、旋转/锁定、网络高亮、尺寸/孔/禁布区及问题定位。明确首版支持范围，不以参考库条目代表已支持真实 IC 全流程。
5. 补完整工程与制板包：检查报告、源证据索引、规则/库/工具身份及逐文件哈希；导出后重读核对，在干净 Windows 环境打开工程并复核。
6. 配置锁定版本的真实 KiCad/Freerouting，执行 RC、二极管、晶体管等链路，并在固定 30 个支持案例上测实际布线成功率、耗时和失败原因。加入错脚、异网短接、断线、规则变化、铺铜变化、取消与源版本更新等负例；真实工具缺失必须标为跳过/未验收。
7. 将 PCB 测试纳入 CI，补 wheel/Windows 发布检查。所有 P1 缺陷关闭、M1 必要交互完成、真实 M2 链路与导出包复验通过后，再将阶段文档改为“完成”。

可保留现有模块和接口框架继续修复；本次不要求推倒重做。正式完成的判断应以可靠检查、完整产物和可复现真实链路为依据。
